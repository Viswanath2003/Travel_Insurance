## 1. Schema Organization

Each microservice owns a dedicated MySQL schema (database). All schemas reside on the same MySQL instance in local deployment.

```
MySQL Instance (localhost:3306)
├── ins_auth          — auth-service         (identity, RBAC)
├── ins_product       — product-service      (catalog, plans, coverages, add-ons, zones)
├── ins_rule          — rule-engine-service  (rules, conditions, actions, execution logs)
├── ins_policy        — policy-service       (quotes, policies, snapshots, wordings)
├── ins_underwriting  — underwriting-service (UW cases, decisions, escalations)
├── ins_claims        — claims-service       (claims, documents, decisions, payments)
├── ins_field         — field-service        (assignments, reports, evidence)
├── ins_document      — document-service     (templates, generated documents, versions)
├── ins_notification  — notification-service (templates, notifications, delivery log)
├── ins_audit         — audit-service        (immutable audit log — INSERT only)
└── ins_workflow      — shared infrastructure (workflow state machine definitions)
```

**Cross-schema referencing:** Services reference foreign entities by storing the remote ID as a plain VARCHAR column (e.g., `policy_id`, `customer_id`). Referential integrity across schemas is enforced at the application layer, not via DB foreign keys. Within a schema, all FK constraints are enforced at the DB level.

## 2. Naming Conventions

| Element | Convention | Example |
|---|---|---|
| Schema names | `ins_{domain}` | `ins_auth`, `ins_policy` |
| Table names | snake_case, plural | `user_roles`, `plan_coverages` |
| Column names | snake_case | `policy_number`, `created_at` |
| Primary key | `id VARCHAR(36)` — UUID | `id` |
| Foreign keys | `{ref_table_singular}_id` | `plan_id`, `customer_id` |
| Boolean columns | `is_` prefix | `is_active`, `is_locked` |
| Timestamp columns | `*_at` suffix | `created_at`, `expires_at` |
| Actor columns | `*_by` suffix | `created_by`, `decided_by` |
| Unique keys | `uq_{table}_{cols}` | `uq_plan_addon` |
| Indexes | `idx_{table}_{cols}` | `idx_claims_customer_id` |
| Enum-like VARCHAR | `{col}_code` | `role_code`, `addon_code` |
| Reference numbers | `{entity}_reference` | `claim_reference`, `policy_number` |

**Universal columns on all mutable tables:**
- `id VARCHAR(36) PRIMARY KEY` — UUID generated by application
- `created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`
- `updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
- `created_by VARCHAR(36)` — user ID of creator (null for system-generated)
- `version BIGINT DEFAULT 0` — on high-contention entities (optimistic locking)

**Exception:** `audit_logs` has NO `updated_at`, NO `is_active` — it is append-only and immutable.

## 6. Versioning Strategy

Three levels of versioning are applied:

### Level 1 — Configuration Version (Plans, Rules, Templates)
Applies to: `plans`, `rule_definitions`, `document_templates`

```
Each entity has a `version` INT column and a `status` column:
  DRAFT    → being edited, not live
  ACTIVE   → current live version
  SUPERSEDED → replaced by newer version (retained for historical reference)

On publish:
  1. Current ACTIVE version → status = SUPERSEDED
  2. New version record created with incremented version number
  3. *_versions table stores a JSON snapshot of the entity at publish time
  4. effective_from = NOW() (or scheduled future date)

Policies and quotes store which plan_version was used at quote time.
Rule execution logs store which rule_version was used at evaluation time.
```

### Level 2 — Document Version (Generated PDFs)
Applies to: `generated_documents`, `document_versions`

```
On re-generation (e.g., post-endorsement):
  1. existing generated_document: is_latest = false, current_version incremented
  2. New document_versions record created with new file path and version number
  3. Old file retained on filesystem (never deleted)
  
Download API returns:
  - latest version by default
  - specific version by ?version= parameter
```

### Level 3 — Snapshot Immutability (Policies, Claims)
See Section 7 (Snapshot Strategy).

## 7. Snapshot Strategy

Snapshots capture complete entity state at a specific point in time. They are **never updated** — only created.

### Policy Snapshot (ins_policy.policy_snapshots)
```
Created at:  Policy activation (status → ACTIVE)
             Policy endorsement
             Policy renewal

snapshot_data JSON contains:
{
  "policyNumber": "POL-20260501-000123",
  "issuedAt": "2026-05-01T10:30:00",
  "customer": { "id", "fullName", "email" },
  "plan": { "id", "code", "name", "version": 3 },
  "travelers": [ { "name", "dob", "age", "passport", "riskScore" } ],
  "coverages": [ { "typeCode", "name", "limit", "deductible", "currency" } ],
  "addons": [ { "code", "name", "premium" } ],
  "premiumBreakdown": { "basePremium", "loadings", "discounts", "totalPremium" },
  "riskScore": 45,
  "riskLevel": "MEDIUM",
  "rulesUsed": { "riskRuleVersion": 3, "premiumRuleVersion": 7 },
  "policyWording": { "code", "version": 2, "effectiveFrom" },
  "destinationZone": { "zoneCode", "countryCode" }
}

Purpose: Claims processing ALWAYS reads from policy_snapshot, never live policy.
         This ensures claims are adjudicated against the terms that were in force
         at the time the policy was issued.
```

### Claim Snapshot (ins_claims.claim_snapshots)
```
Created at:  Claim submission (type: SUBMISSION)
             Final decision (type: DECISION)
             Settlement (type: SETTLEMENT)

snapshot_data JSON contains (DECISION type):
{
  "claimReference": "CLM-20260501-000045",
  "submittedAt": "2026-05-15T09:00:00",
  "policySnapshotId": "uuid",
  "claimType": "MEDICAL_EXPENSES",
  "incidentDate": "2026-05-10",
  "claimedAmount": 5000.00,
  "coverageLimit": 100000.00,
  "documentsSubmitted": [...],
  "checklistCompletion": { "total": 4, "submitted": 4 },

```

### Quote Snapshot (ins_policy.quote_snapshots)

## 8. Audit Strategy

### Immutability Enforcement (3 layers)
```
Layer 1 — Database:
  audit_logs table has NO updated_at, NO deleted_at, NO is_active
  DB user `ins_audit_svc` granted: INSERT, SELECT on ins_audit.audit_logs
  DB user `ins_audit_svc` NOT GRANTED: UPDATE, DELETE, DROP, ALTER

Layer 2 — Application:
  audit-service exposes only POST /audit/events and GET /audit/events
  No PUT, PATCH, DELETE endpoints exist
  Incoming POST requests INSERT and return — no read-modify-write

Layer 3 — Schema:
  audit_logs has no updatable columns
  occurred_at is DEFAULT CURRENT_TIMESTAMP(6) — set on insert, never writable after
```

### What Gets Audited
Every service publishes an AuditEvent after each meaningful state change:

| Domain | Events Audited |
|---|---|
| Auth | LOGIN, LOGIN_FAILED, LOGOUT, PASSWORD_RESET, ACCOUNT_LOCKED, ROLE_ASSIGNED |
| Policy | QUOTE_CREATED, QUOTE_EXPIRED, POLICY_CREATED, POLICY_ACTIVATED, POLICY_CANCELLED |
| Underwriting | UW_CASE_CREATED, UW_ASSIGNED, UW_APPROVED, UW_DECLINED, UW_REFERRED, UW_ESCALATED, SLA_BREACHED |
| Claims | CLAIM_SUBMITTED, CLAIM_REVIEWED, CLAIM_DECIDED, CLAIM_SETTLED, FIELD_ASSIGNED |
| Field | FIELD_ACCEPTED, FIELD_REPORT_SUBMITTED |
| Admin | PLAN_PUBLISHED, RULE_PUBLISHED, TEMPLATE_PUBLISHED, RBAC_CHANGED, USER_DEACTIVATED |
| Documents | DOCUMENT_GENERATED, DOCUMENT_DOWNLOADED |

### Audit Event Structure
```
audit_logs columns:
  audit_id       — UUID (unique event identifier)
  correlation_id — X-Correlation-ID from gateway (traces a request through all services)
  event_type     — e.g., POLICY_ACTIVATED
  entity_type    — POLICY / CLAIM / USER / RULE / PLAN
  entity_id      — the specific entity's ID
  actor_user_id  — who did it (null for SYSTEM events like SLA breach)
  actor_role     — their role at time of action
  actor_ip       — IP address from gateway header
  old_state      — JSON of state before change
  new_state      — JSON of state after change
  details        — human-readable description
  service_name   — which microservice published this event
  occurred_at    — DATETIME(6) — microsecond precision
```

## 9. Index Strategy

### Primary Key
All tables use `id VARCHAR(36)` UUID primary key. MySQL creates a B-tree clustered index on this.

### Query-optimized Indexes

**ins_auth:**
- `users(email)` — UNIQUE — login lookup
- `users(username)` — UNIQUE — login lookup
- `users(status)` — filter active users
- `user_sessions(user_id, is_revoked)` — find active sessions per user
- `otp_tokens(user_id, is_used, expires_at)` — find valid OTPs

**ins_policy:**
- `quotes(customer_id, status)` — My Quotes list
- `quotes(expires_at, status)` — expiry cleanup job
- `policies(customer_id, status)` — My Policies list
- `policies(policy_number)` — UNIQUE — policy lookup
- `policies(status, risk_level)` — underwriting routing filter
- `policy_snapshots(policy_id)` — snapshot fetch by policy

**ins_underwriting:**
- `uw_cases(current_state, assigned_to_user_id)` — queue per underwriter
- `uw_cases(sla_due_at, current_state)` — SLA monitoring scheduler
- `uw_cases(policy_id)` — case lookup by policy

**ins_claims:**
- `claims(customer_id, current_state)` — My Claims list
- `claims(assigned_officer_id, current_state)` — Claims Officer queue
- `claims(policy_id)` — claims for a policy
- `claims(sla_due_at, current_state)` — SLA monitoring
- `claim_reference` — UNIQUE

**ins_audit:**
- `audit_logs(entity_type, entity_id)` — per-entity trail
- `audit_logs(actor_user_id)` — per-user trail
- `audit_logs(occurred_at)` — time range queries
- `audit_logs(event_type)` — event type filter
- `audit_logs(correlation_id)` — request tracing

**ins_rule:**
- `rule_definitions(rule_type, status)` — load active rules by type
- `rule_execution_logs(execution_batch_id)` — fetch trace by batch
- `rule_execution_logs(context_type, context_id)` — trace per policy/claim

## 10. Constraint Rules

| Rule | Implementation |
|---|---|
| UUIDs as PKs | `VARCHAR(36)`, application generates UUID before INSERT |
| No hard deletes | `is_active BOOLEAN` or `status` column; no DELETE in service code |
| Optimistic locking | `version BIGINT DEFAULT 0` on uw_cases, policies; Spring `@Version` |
| Immutable audit | INSERT-only DB user for ins_audit |
| Policy immutability | No UPDATE after `status = ACTIVE`; snapshot captures state |
| Soft enums | Use VARCHAR for extensible codes (claim_type, coverage_code); use ENUM only for fixed finite sets (gender, payment_method) |
| Cross-schema refs | Stored as VARCHAR columns, not FK constraints; validated at service layer |
| Snapshot integrity | snapshot_data columns are JSON NOT NULL; never NULL, never updated |
| Password storage | Only BCrypt hashes stored; never plaintext |
| Sensitive data | OTP hash is BCrypt of the OTP value; never the OTP itself |

```
6.  ins_underwriting— V05 underwriting tables + V19 seed: SLA config
7.  ins_claims      — V06 claims tables + V16 seed: claim types, checklist config
8.  ins_field       — V07 field tables
9.  ins_document    — V08 document tables + V17 seed: document templates
10. ins_notification— V09 notification tables + V18 seed: notification templates
11. ins_audit       — V10 audit tables

```
